* Overview

~tsmctl~ (=bin/scripts/tsmctl=) is a kubectl-style command line for the data TradeSkillMaster leaves on disk. It answers business questions: what made money, what is dead stock, how much capital is tied up in flips, what the whole operation is worth, and what is cheap on the auction house right now. It is a single Python file using only the standard library (Python 3.12+).

It also reads Altoholic's DataStore and Syndicator (the data addon behind Baganator) when they are installed. They add what TSM does not keep: every posted auction with its price and time left, mail with its expiry, character level, race and played time, void storage, currencies and known recipes. With them ~tsmctl attention~ tells you which characters on which realms need a login, and why. All three sources are optional and detected per account; TSM is no longer required.

It is *read-only* on the WoW side. It never writes to SavedVariables or AppData. When the WoW install is on another machine, it runs only ~find~ and ~tar c~ there over ssh and mirrors the files into a local cache. Besides its cache, it only writes what you ask for: a report with ~--save~, an export with ~export --file~, the systemd units with ~venture install-units --write~; ~venture push~ keeps a lock and the last pushed body's hash under the cache.

Everything goes to stdout by default. ~--save~ writes an org file into the notes repo (or a path you give) and links it from that directory's =00_index.org=.

It also feeds VENTURE (the ERP/CRM in =~/source/projects/venture=): ~tsmctl export --format venture~ writes everything it knows as VENTURE's JSON-lines protocol, and ~tsmctl venture push~ sends that to a VENTURE data source, by hand or from systemd user units that fire when WoW writes its files. See [[*VENTURE][VENTURE]].

* Quick start

#+begin_src bash
tsmctl status                       # where the data came from, how fresh, warnings
tsmctl attention                    # who needs a login: expiring auctions and mail, stale alts
tsmctl get chars --by login         # characters per WoW account (login), with a per-login summary
tsmctl get auctions --expiring 6h   # posted auctions ending soon, with price and time left
tsmctl get mail --expiring 3d       # mail about to expire
tsmctl report                       # last 30 days of the business on one page
tsmctl report --since 7d --save     # same, written to the notes repo as org
tsmctl pnl --by day --since 14d     # daily profit & loss
tsmctl flips --open                 # stock bought and not yet sold
tsmctl sellthrough --max-rate 20    # items that keep expiring
tsmctl export --check               # what a VENTURE push would carry, checked against the contract
tsmctl venture push --wait          # push it to the configured VENTURE data source
tsmctl deals --realm "Moon Guard"   # buy candidates from the last realm scan
tsmctl describe item "Card of Omens"
#+end_src

The dotfiles ship =.config/tsmctl/config.yaml= with ~host: mob-zach~. On mob-zach itself that host name is recognised as the local machine and the install is read directly; everywhere else it is read over ssh.

* Data sources

** SavedVariables: =WTF/Account/<account>/SavedVariables/TradeSkillMaster.lua=

One file per WoW account folder. tsmctl reads every account and merges them (or only ~--account~ ones). WoW only writes this file on logout or ~/reload~, so it trails a live session.

TSM stores keys as =scope@scopeKey@section@name=:

| Scope | Key example                       | What tsmctl uses                                                                 |
|-------+-----------------------------------+----------------------------------------------------------------------------------|
| =s@=  | =Drgold - Alliance - Thorium ...= | per character: =money=, =classKey=, =playerProfessions=, =goldLog=, =goldLogLastUpdate=, =*Quantity= |
| =r@=  | =Thorium Brotherhood=             | per realm ledger: =csvSales=, =csvBuys=, =csvIncome=, =csvExpense=, =csvExpired=, =csvCancelled= |
| =f@=  | =Alliance - Thorium Brotherhood=  | =guildVaults=, =guildGoldLog=, =characterGuilds=, =expiringAuction=, =expiringMail=, =crafts= |
| =g@=  | (global)                          | =warbankMoney=, =warbankQuantity=, =warbankGoldLog=, =warbankGoldLogLastUpdate=, =vendorItems= |
| =p@=  | =Default= (profile)               | =userData items= and =groups= (TSM groups)                                      |

The file also holds =TSMItemInfoDB=, TSM's item cache: names and item strings joined with =\x02=, plus a packed 24-character record per item (item level, vendor sell, max stack, class, quality, expansion...) in a little-endian base-64 alphabet. tsmctl decodes it for names, quality and vendor prices.

*** Professions and crafts

=playerProfessions= (per character) holds each profession's =level=, =maxLevel= and =isSecondary=. =crafts= (per faction-realm, from TSM's Crafting module once a profession window has been opened) is keyed =c:<spell id>= and holds the recipe's =name=, =profession=, the =itemString= it makes and =numResult=, its =mats= (=i:ID= reagents with quantities; =o:...= optional and quality reagents are choices, not costs, and are not counted), and =players= who know it. The spell id is DataStore's recipe id, which is how names and products are joined onto DataStore's lists. The same spell on two realms is one craft known by both realms' players.

*** Ledger semantics (verified against the TSM addon source)

- Sales and buys: =itemString,stackSize,quantity,price,otherPlayer,player,time,source=. =price= is *per item*, =quantity= is the total units (TSM merges identical records within 5 minutes and adds to =quantity=).
- AH sale prices are recorded *after* the 5% AH cut: TSM stores =(bid - ahcut) / quantity=. Purchases are what you paid.
- =source= is =Auction=, =Vendor=, =Trade= or =COD=.
- Income/expense rows: =type,amount,otherPlayer,player,time= (=Postage=, =Repair Bill=, =Money Transfer=...).
- Expired/cancelled rows: =itemString,stackSize,quantity,player,time=.
- Mail-based records are dated =now + (daysLeft - 30) days=. Mail with a long expiry (WoW Token sales) lands in the future; tsmctl re-dates anything after the file's save time to the save time and warns.
- Retail gold logs are =minute,copper= rounded to 1,000g, so gold history is coarse.

** Altoholic DataStore: =WTF/Account/<account>/SavedVariables/DataStore*.lua= (optional)

Altoholic stores its data through the DataStore family of addons. tsmctl reads seven files per account: =DataStore.lua=, =DataStore_Characters.lua=, =DataStore_Auctions.lua=, =DataStore_Mails.lua=, =DataStore_Containers.lua=, =DataStore_Currencies.lua= and =DataStore_Crafts.lua=. The files are CRLF Lua like any SavedVariables.

DataStore keys every character by a small integer: =DataStore_CharacterIDs.List= in =DataStore.lua= is ="Default.<Realm>.<Name>"= in id order, and each module stores its per-character tables as arrays indexed by that id (sparse arrays are written with explicit =[n] = ...= keys). Guilds work the same through =DataStore_GuildIDs=, and =DataStore_CharacterGuilds[id]= is the character's guild id. Without =DataStore.lua= nothing can be attributed, so that account's DataStore data is skipped with a warning. =DataStore_ConnectedRealms= says which realms are connected, which matters for guild banks (below).

| File                         | Table                                         | What tsmctl uses                                                                                                                                             |
|------------------------------+-----------------------------------------------+--------------------------------------------------------------------------------------------------------------------------------------------------------------|
| =DataStore_Characters.lua=   | =DataStore_Characters_Info[id]=                | =money= (copper), =played=, =lastUpdate=, =lastLogoutTimestamp=, =zone=, =BaseInfo= packed as bits 0-6 level, 7-10 class id, 11-17 race id, 18-19 gender      |
| =DataStore_Auctions.lua=     | =DataStore_Auctions_AuctionsList[id]=          | one pipe-separated string per auction (format below the table)                                                                                               |
|                              | =DataStore_Auctions_Characters[id]=            | =lastAuctionsScan=: expiry is =lastAuctionsScan + timeLeftSeconds=                                                                                             |
| =DataStore_Mails.lua=        | =DataStore_Mails_Characters[id].Mails=         | one entry per attachment (=itemID=, =count=, =link=) and one per money/letter, each with =sender=, =subject=, =money=, =returned=, =lastCheck=, =daysLeft= |
|                              | =...MailCache=                                 | mail an alt sent that the recipient has not seen yet (30 days from sending)                                                                                    |
| =DataStore_Containers.lua=   | =DataStore_Containers_Characters[id].Containers[bagID]= | =items[slot]= = count + (itemID << 16), =links[slot]=                                                                                               |
|                              | =DataStore_Containers_Warbank[tab]=            | warband bank tabs (bag ids 12-16), same packing, no timestamp                                                                                                |
|                              | =DataStore_Containers_Guilds[guild id].Tabs=   | guild bank tabs, each with =ClientTime= (when it was last seen)                                                                                               |
|                              | =DataStore_Containers_VoidStorage[id]=         | void storage, always the old 10-bit count                                                                                                                    |
| =DataStore_Currencies.lua=   | =DataStore_Currencies_Characters[id].Totals=   | =[currencyID]= = quantity + (earned this week << 20); caps in =DataStore_Currencies_Max=                                                                       |
| =DataStore_Crafts.lua=       | =DataStore_Crafts_Characters[id].Professions=  | =Crafts[category]= lists packed recipes: bits 0-1 difficulty, 2 learned, 3-4 rank, 5-6 ranks, 7+ recipe (spell) id; category names in =..._RecipeCategories= |

An auction string is =AHZone|itemID|quantity|bidder|bidAmount|buyoutAmount|timeLeftSeconds|auctionID=, for example =0|112294|3||0|3005100|86392|1637379826=.

Details that are easy to get wrong:

- Container bag ids: 0-4 bags and 5 the reagent bag (place =bag=), 6-11 the character bank tabs (6-12 bank bags before 11.2) and -1 the old main bank (=bank=), -3/-7 the reagent bank (=reagent_bank=), -5/-6 void storage (=void=), -2 the classic keyring (=bag=).
- Slot counts moved from 10 to 16 bits in DataStore 10.2.013 and old characters still have the 10-bit form. DataStore tells them apart by bits 13-15 (zero in the 16-bit form) and so does tsmctl.
- Battle pets in bags store their icon id where the item id goes; tsmctl takes the pet from the link instead (=p:species:level:quality=).
- A character's bank only counts once DataStore has seen it open (=bankInfo= is set then); until then its empty bank tables would wrongly say the bank is empty.
- =buyoutAmount= is a unit price: it is =C_AuctionHouse='s owned-auction buyout, which Auctionator also multiplies by the quantity for its totals. Sold auctions are not listed (they are in the mail).
- Currency names are stored without ids: =Characters[id].Currencies= is a list packed as bits 0-7 header, 8-17 index into =Catalog.List=, 18+ count. tsmctl names an id when the listed count pins it down on every character that lists it; a currency nobody holds stays unnamed.
- Recipe names and result items are not stored, only recipe (spell) ids; ~get recipes~ names them, and adds what each makes, from TSM's crafts (see [[*Professions and crafts][Professions and crafts]]), and links each one on Wowhead.
- No faction is stored: it comes from the race (Pandaren id 24 is neutral), unless TSM or Syndicator says.

** Syndicator: =WTF/Account/<account>/SavedVariables/Syndicator.lua= (optional)

=SYNDICATOR_DATA.Characters= is keyed ="Name-RealmNormalized"=. Each character has =details= (=character=, =realm=, =faction=, =race=, =className=, =guild= as ="Guild-HomeRealm"=), =money=, =bags=, =bank=/=bankTabs=, =void=, =mail= (items with an absolute =expirationTime=), =auctions= (=itemID=, =itemCount=, =itemLink=, =expirationTime= epoch, =auctionID=) and =currencies= (={id = quantity}=). =Warband[1]= is the warband bank (=money=, =bank=) and =Guilds= the guild banks. Nothing in it carries a timestamp, so it only wins where no dated source has the data. Its guild key names the guild's home realm, which tsmctl also takes as evidence that two realms are connected.

** Reconciliation: which copy wins

Where sources overlap, one rule decides, per character gold, per owner and place group of holdings, and per character mail list and currency list:

1. The freshest dated copy wins.
2. Copies within 5 minutes of the freshest count as the same moment (one logout stamps TSM and DataStore a minute or two apart) and the priority TSM, then DataStore, then Syndicator breaks the tie.
3. Undated copies only win when nothing is dated, again by that priority.

The timestamps: TSM has none on its quantity tables, so a character's TSM data is dated by its gold log's last update (=goldLogLastUpdate=, TSM's best "last seen"), the warband bank by =warbankGoldLogLastUpdate=, and guild vaults are undated. DataStore dates character data by its =lastUpdate=, auctions by =lastAuctionsScan=, mail by the mailbox =lastUpdate= and guild tabs by =ClientTime=; its warband bank is undated. Syndicator is undated.

Holdings are compared per place group, not per place, because TSM's bag count includes the reagent bag and its bank count the reagent bank: the groups are bag, bank (bank and reagent bank), void, mail, auction, warbank and guild. The winner's holdings replace every other source's for that owner and group. Slot-level sources are summed per item and place.

Guild banks: TSM keeps one guild vault per faction and realm, so a guild seen from two connected realms is stored (and was counted) twice. Guild sets are therefore matched on the guild name and the connected-realm group. DataStore's copies of one guild are merged tab by tab, each tab from the copy that saw it last; TSM's copies collapse to the one with the most distinct items. Before this, a guild visited from two connected realms was counted twice in inventory and net worth.

Auctions are joined on the auction id: DataStore brings the buyout, bid, quantity and its time-left expiry, Syndicator the item link and an absolute expiry (which wins). Auctions only one source knows are kept: Syndicator keeps expired auctions that DataStore already dropped, and those are exactly the ones waiting in the mailbox.

Characters are matched on name and realm. Level, race, played time, zone and last seen come from DataStore; a character TSM never saw is created from DataStore or Syndicator. Last seen is the latest of TSM's gold log update and DataStore's =lastUpdate= / =lastLogoutTimestamp=.

~status~ shows which source won how many owner/place groups. ~--sources~ (or =sources:= in the config, or =TSMCTL_SOURCES=) restricts reading to some sources, which also shows what each one says on its own.

** AppData: =Interface/AddOns/TradeSkillMaster_AppHelper/AppData.lua=

Written by the TSM desktop app (~tsm-app~). It is a series of ~LoadData("TAG","realm-or-region",[[return {downloadTime=...,fields={...},data={{item,v1,v2},...}}]])~ calls. Values are base-32 integers; a bare number item is =i:<id>=.

| Tag                                     | Scope                | Fields                                                   |
|-----------------------------------------+----------------------+----------------------------------------------------------|
| =AUCTIONDB_NON_COMMODITY_DATA=          | realm                | minBuyout, numAuctions, marketValueRecent                |
| =AUCTIONDB_NON_COMMODITY_SCAN_STAT=     | realm                | marketValue                                              |
| =AUCTIONDB_NON_COMMODITY_HISTORICAL=    | realm                | historical                                               |
| =AUCTIONDB_COMMODITY_*=                 | region (stackables)  | same fields, apply to every realm                        |
| =AUCTIONDB_REGION_STAT=                 | region               | regionMarketValue                                        |
| =AUCTIONDB_REGION_SALE=                 | region               | regionSale, regionSoldPerDay, regionSalePercent (both x1000) |
| =AUCTIONDB_REGION_HISTORICAL=           | region               | regionHistorical                                         |

Realm lookups try the realm's own data, then the region commodity data; item lookups try the exact item string, then the base item. Realms not in the TSM app's realm list have no realm data (=tsmctl status= lists them).

* Logins

Every folder under =WTF/Account/= is one *login*: the WoW account (licence) a session signs in with. A legacy account shows up under its account name (=ZAKMANN=), a Battle.net licence as =<id>#<n>= (=12345678#1=). Switching logins means logging out to the launcher, which costs far more than switching realms, so tsmctl shows which login every character belongs to and can group by it. A login is labelled the way the launcher shows it: a Battle.net licence folder =<number>#<n>= is =WoW<n>= (=53141745#1= is =WoW1=), and a legacy account name is its own label (=ZAKMANN=). When two Battle.net accounts both have a =WoW1=, each carries its account number, =WoW1 (11111111)=. =account_labels= overrides any of these, and ~--login~ takes the label as well as the folder.

** Labels and Battle.net groups

#+begin_src yaml
account_labels:            # a label per folder; shown as the login and sent to VENTURE as its name
  ZAKMANN: Main
  "12345678#1": Alt
battlenet_groups:          # folders that belong to one Battle.net account
  bnet-main: [ZAKMANN, "12345678#1"]
warband: per_account       # or shared
#+end_src

- A folder without a label is labelled with its own name.
- A folder may be in one group only (it belongs to one Battle.net account); a group must list at least one folder.
- ~--login~ is an alias of ~--account~ and takes a folder name, a label or a group name (all its folders), case-insensitively: ~tsmctl --login Main attention~, ~tsmctl --login bnet-main get chars~.
- The keys are config-only. Mapping keys are kept exactly as written; quote a folder name if YAML would read it otherwise.

** Warband banks: per account or shared

The warband bank is written into every folder's SavedVariables: TSM's =warbankMoney= / =warbankQuantity=, DataStore's =DataStore_Containers_Warbank=, Syndicator's =Warband[1]=. What that copy describes depends on how Blizzard scopes the bank, and tsmctl cannot tell from the files, so it is a setting:

- =per_account= (the default, and what tsmctl always did): each folder has its own warband, the VENTURE account =warbank:<folder>= with that login.
- =shared=: the folders of one =battlenet_groups= entry share one warband, the VENTURE account =warbank:<group>= with no login (it belongs to none of them alone) and =attrs.login_group=. Folders in no group keep their own. ~warband: shared~ with no groups merges nothing and says so.

With =shared= each folder's copy is an observation of the same bank, so the copies are *compared, never summed*: summing would count every item and every gold piece once per copy. Within a folder the sources compete as everywhere else ([[*Reconciliation: which copy wins][Reconciliation]]); then across the group's folders the gold and the contents are each taken from the freshest copy. A copy is dated by its own timestamp (TSM's =warbankGoldLogLastUpdate=) or, when it has none (DataStore, Syndicator), by when WoW wrote that folder's file of that source; =pick_freshest()= decides, so dated copies within five minutes go by source priority, and a remaining tie by folder name. The losing copies' items are dropped. ~status~ shows, per login, its group, its warband and whose copy the shared contents came from.

A group's name that is also the name of a folder outside it is refused under =shared= (both would be =warbank:<name>=).

An empty warband that a source read is still a warband: TSM's empty =warbankQuantity= table and Syndicator's =Warband= entry with an empty =bank= cover its holdings, and a known gold of 0 is sent as a balance of ="0"=, so VENTURE empties it instead of keeping old rows. DataStore's empty =DataStore_Containers_Warbank= is not taken as coverage: it has no timestamp, and an empty table cannot be told apart from one that was never filled.

** More than one machine

#+begin_src yaml
hosts:
  - host: mob-zach
    accounts: [ZAKMANN, "12345678#1"]
  - host: laptop
    wow_dir: "~/Games/World of Warcraft"
    prefix: laptop-
#+end_src

Each entry is a machine read like =host= / =wow_dir= / =flavor= (which are its defaults; a local entry says ~host: localhost~), and the data of all of them is merged. =accounts= keeps only those folders on that machine. Every machine has its own mirror under the cache.

- A folder is known by its entry's =prefix= plus its name (=laptop-ZAKMANN=). That name is the login everywhere: in =account_labels=, =battlenet_groups=, ~--login~ and the VENTURE login key.
- A folder name found on two machines is refused unless a prefix (or an =accounts= list) tells them apart: two logins of one name would quietly become one. If it really is the same login on two machines, read it on one of them only.
- A machine that cannot be read (and has nothing cached) is skipped with a warning; the others still load, ~status~ lists it under Hosts, and an export without it leaves its accounts untouched in VENTURE. A shared warband one of whose folders was not read is left out of the export (see [[*Logins in the export][Logins in the export]]).
- ~--host~, ~--local~, ~--wow-dir~ or ~--flavor~ on the command line, or =$TSMCTL_HOST= / =$TSMCTL_WOW_DIR=, name one install and the list is not read.
- Market data is region-wide: the newest =AppData.lua= across the machines is used.
- ~venture push --settle~ and ~venture install-units~ watch the machines that are local.

* Commands

All commands accept the common options (data source, filters, output) before or after the command name.

** status

Data source (local or ssh + cache; with =hosts:= every machine and which were skipped), counts of characters, auctions, mail, currency balances and recipes, a Sources table (per account and source: used, missing, not selected or error, files, when the file was saved, "data as of" from the newest timestamp inside the data, and notes), how many owner/place groups each source won in reconciliation, a Hosts table (with =hosts:=), a Logins table (per folder: its label, Battle.net group, characters, its warband or the shared one and whose copy it is), every file with its source and age, ledger row counts and latest record per kind, every AppData dataset with its download age, and warnings: stale SavedVariables, a TSM app that has not synced for 6h+, trimmed accounting, realms with no market data, and every warning raised while loading (a missing or unreadable DataStore module, a corrupt Syndicator file).

** attention

The ops view: what needs a character to log in, one row per character and reason, most urgent first.

1. Mail expiring within ~--mail-expiring~ (default 3 days) that holds gold or items: missed, it bounces or is deleted.
2. Auctions that have already expired: sold or returned, waiting in the mailbox.
3. Auctions ending within ~--expiring~ (default 12 hours): relist.
4. Other mail holding gold or items.
5. Characters not seen for longer than ~--stale~ (default 14 days).

Within a reason the earliest deadline comes first. Each row shows the count, the value (auction buyouts; Syndicator-only auctions at the price source; gold plus item value for mail; the character's gold for stale ones) and the deadline relative to now (negative = already past). Above the table is the summary to act on: =- log in to <realm>: <characters> (<reasons>)=, realms ordered by their most urgent row, and a line listing stale characters. With more than one login it is grouped by login first, because switching logins is the costly move: =- log into <login> → <realm>: <characters> (<reasons>)=, the most urgent login first and its realms most urgent first, and the stale line names each character's login. The table has a Login column; ~--by login~ orders it by login, then urgency (the default ~--by priority~ is urgency alone). Characters for which neither DataStore nor Syndicator recorded auctions or mail fall back to TSM's own =expiringAuction= / =expiringMail= (each character's first expiry). Durations take =30m=, =6h=, =3d=, =2w= (=m= is minutes here); a bare number is hours for ~--expiring~ and days for the other two.

The optional ~query~ filters ledger, inventory and prices by item (name substring, id, =i:ID= or Wowhead URL).

** describe item|char|realm|group <name>

- item: identity (quality, ilvl, class, vendor prices, TSM group), AuctionDB prices per realm plus region stats, your history (units, revenue, avg/min/max sale, cost, profit, sell-through), holdings by owner and location, recent transactions, and what each unit nets today at your average cost.
- char: level, class, race, faction, guild, gold (and which source it came from, as of when), inventory value, posted auctions and their buyout value, gold and items waiting in mail, last seen, played time, zone, P&L for the window, professions, its auctions soonest to end first, mail with gold or items, currencies, most valuable holdings and recent transactions. ~Name-Realm~ may be shortened to a unique prefix (=Drgold-Thor=).
- realm: characters and gold, market snapshot age and size, P&L.
- group: per-item performance for a TSM group and its subgroups.

** search <text>

Item lookup against the TSM item cache, with value, units you sold, units you hold and TSM group.

** pnl

Cash-basis profit and loss: AH sales (net of cut), vendor sales, trade/COD, other income, purchases, expenses, net. ~--by day|week|month|year|realm|char|login|source|group|item|none~; ~login~ buckets a row by its character's login. Time buckets also show a running cumulative net. Default window 30 days.

Cash basis means a week of heavy buying shows as a loss even if the stock is worth more than you paid; ~flips~ and ~networth~ show the other side.

** top items|chars|buyers|sellers

- items ~--by profit|revenue|sold|roi|margin|velocity|expired|spent|sales~: per-item performance. Profit matches units sold against average purchase cost; items never bought (farmed, crafted) have no cost basis, so profit equals revenue.
- chars: P&L per character.
- buyers: who buys from you (customers). sellers: who you buy from (suppliers). Vendor rows are excluded.

** flips

For every item bought in the window: units bought and average cost, units sold *since the first purchase* and average sale, realized profit and ROI, open units, unrealized P/L at the price source after the AH cut, and a status: =CLOSED=, =SELLING=, =OPEN= (nothing sold yet), =STALE= (still holding, no activity for 7 days) or =LOSING= (selling below cost). The summary shows capital still tied up. ~--open~ keeps only open positions; ~--min-spent~ hides small ones.

** sellthrough

Per item AH outcomes (sold, expired, cancelled) and sell-through = sold / (sold + expired + cancelled), with the region sale rate and a verdict: =healthy= (50%+), =vendor it= (market after cut is at or below vendor price), =dead market: stop posting= (under 15% and the region barely sells it), =overpriced: lower or wait= (under 15% but the region sells it), =slow: watch=. ~--min-listings~ (default 3), ~--max-rate~ (percent).

** networth

Liquid gold (characters, warbank, guild banks from the last guild gold log) plus goods (bags, bank, mail, warbank, guild vaults) plus posted auctions, valued two ways side by side:

- *Minimum*: =price_source= (default =check(dbregionsaleavg, min(dbmarket, dbregionsaleavg), vendorsell)=). This is what goods actually sell for region-wide, capped at the realm market, or vendor price if they never sell. Treat it as the floor.
- *Market*: =market_source= (default =first(dbmarket, dbregionmarketavg, vendorsell)=). This is what goods are listed at. It is inflated by items that almost never sell, so the summary also shows the market-minus-minimum gap and how much of it comes from items with no region sales at all.

Each view is shown gross and after the AH cut. ~--valuation both|min|market~ (default both), ~--by realm|char|location|login~ (by login a shared warband is a bucket of its own and guild banks are =(guild banks)=). With both, the table shows holdings and totals for each view, and ~-o wide~ adds the goods/on-AH split. Unpriced holdings (soulbound, never on the AH) count as zero and are reported.

** deals

Scans one realm's last AuctionDB snapshot. An item qualifies when its buy price (~--buy-source~, default =dbminbuyout=) is at most ~--max-pct~ (70) percent of the sell reference (~--sell-source~, default =first(dbregionsaleavg, dbmarket)=), the net profit per unit after the cut is at least ~--min-profit~ (10g), and the region sale rate is at least ~--min-sale-rate~ (0.05). Ranked by EV per listing = net profit x region sale rate. ~--commodities~ adds region-wide stackables, ~--no-pets~ skips battle pets, ~--max-buy~ caps the price. The snapshot is the TSM app's last scan, not the live AH; check in game before buying.

** report

The business on one page, default window 30 days:

1. Summary: revenue split, purchases, expenses, net cash flow (total and per day), realized flip profit, AH sell-through, gold change from the gold log, liquid gold, net worth both minimum and market, and highlights (best earners, items sold below cost, dead stock).
2. P&L by day (14 days or less), week (120 days or less) or month.
3. Top products by profit.
4. Flips: spent, realized, capital tied up, unrealized.
5. Dead and slow stock.
6. Top holdings by value (minimum valuation).
7. Gold by character.
8. Deals, with ~--deals~.
9. Method notes.

~--top N~ sets rows per section; ~--sections summary,pnl,...~ picks sections.

** export --format venture

The whole dataset as VENTURE JSON lines, on stdout or ~--file PATH~ (mode 0600, written to =PATH.part= and renamed). ~--check~ writes nothing and prints counts per message type, what was left out and why, and the result of checking every line against the contract. ~--market scope|all|none~ picks the AuctionDB figures, ~--currency~ the data source's currency, ~--since~/~--until~ narrow the ledger, ~--include-internal~ keeps transfers between your own characters, ~--no-logins~ leaves out login lines and =account.login= for a VENTURE older than them. The format is in [[*VENTURE][VENTURE]].

** venture push|status|recipes|install-units

~push~ exports and POSTs to the configured data source (and, with =venture_recipe_source= set, then the crafts when they changed); ~recipes~ sends the crafts alone (~--dry-run~ shows them); ~status~ shows the settings, the server's health and the source's newest runs; ~install-units~ prints (or ~--write~s) the systemd user units. See [[*VENTURE][VENTURE]].

** paths, config

~paths~ prints resolved locations including the default report file. ~config~ shows each effective setting and where it came from (cli, env, config, default); ~config sample~ prints a commented config.

* Price expressions

A safe subset of TSM custom prices. Sources (~tsmctl get sources~): =dbminbuyout=, =dbmarket=, =dbrecent=, =dbhistorical=, =dbnumauctions=, =dbregionmarketavg=, =dbregionhistorical=, =dbregionsaleavg=, =dbregionsalerate=, =dbregionsoldperday=, =vendorsell=, =vendorbuy=, and your own =avgsell=, =avgbuy=, =minsell=, =maxsell=, =minbuy=, =maxbuy=.

Functions: =min=, =max=, =avg= (ignore missing values), =first= (first present value), =check(cond, then, else)= (=then= when =cond= is present and positive). Operators =+ - * /=, =N%= prefix, money literals =10g=, =50s=, =1g50s=. Missing values propagate through arithmetic.

The default (minimum) valuation is =check(dbregionsaleavg, min(dbmarket, dbregionsaleavg), vendorsell)=; the market valuation (=market_source=) is only used for the market net worth. Items that sell somewhere in the region are valued at the lower of the realm market and the region sale average. Items that never sell region-wide are valued at vendor price. Using =dbmarket= alone valued a stack of 4,000 grey Mammoth Cutters at 16M gold and a single unsold sash at 5M, because both only have troll listings.

* VENTURE

VENTURE keeps an operator's side of a market in a data source's series store: accounts (characters, a warband bank, guild banks), their balances over time, holdings by place, their own listings (positions), mail waiting to be collected (inbound) and an external ledger. tsmctl is the producer for World of Warcraft. The contract is VENTURE's =docs/plugins.org= ("The JSON-lines protocol") and =docs/market-data.org= ("Operator accounts"); this chapter says how tsmctl fills it.

** In VENTURE first

- A currency =GOLD= with exponent 4 (100 copper to the silver, 100 silver to the gold), e.g. ~venturectl create currency code=GOLD name=Gold kind=virtual exponent=4~. Every amount is written as gold with at most four places, so the source's currency must have an exponent of at least 4.
- A data source with provider =push= and that currency: ~venturectl create data_source name="WoW (tsmctl)" provider=push enabled=true currency=GOLD venue_namespace=wow-realm instrument_namespace=wow-item~. The namespaces are the data source's settings, not members of any line.
- An API token with the editor role in the source's organization.

** The stream

One JSON object per line, UTF-8, no header line (protocol 1 has none; the version lives in an exec manifest, not in a push). The order is fixed, and the same files always make the same bytes:

1. =venue= lines: each realm (key: the realm slug, lower case, apostrophes dropped, spaces to =-=; =kind: realm=, =group=: the region), plus =commodities-<region>= and =region-<region>= when AuctionDB figures are included.
2. =instrument= lines for every item and currency referenced below, plain items before their variants.
3. =login= lines, one per account folder read.
4. =account= lines.
5. Per account: its =account_snapshot=, then =balance=, =holding=, =position= and =inbound= lines.
6. =txn= lines, oldest first.
7. Per market venue: a =snapshot=, then its =stat= lines.

Money is a decimal string of gold (=27249501812= copper is ="2724950.1812"=), times are UTC with a =Z=, counts are integers. Strings are cut to 512 bytes on a character boundary.

** Instrument keys

Keys follow the Blizzard plugin's format, so VENTURE can join tsmctl's rows with the Blizzard auction feed:

| TSM item string                     | Key                 | Notes                                                       |
|-------------------------------------+---------------------+-------------------------------------------------------------|
| =i:2770=                            | =2770=              | a plain item                                                |
| =i:9944::3:6655:1692:1692=          | =9944:b1692,6655=   | bonus ids sorted ascending, repeats dropped; parent =9944=  |
| =i:133358::2:7756:13828:1:9:70=     | =133358:b7756,13828= | TSM's modifier pairs are not in the key; kept as =tsm_modifiers= ="9=70"= |
| =i:1420::i13=                       | =1420=              | TSM's level-only form; the level kept as =tsm_levels= ="13"=  |
| =p:1720:25:3=                       | =82800:p1720=       | a caged pet; parent =82800= (Pet Cage)                      |

Items read from links (DataStore, Syndicator) are first turned into the same item strings, so a link's bonus ids land in the same key. Two things cannot match the Blizzard key exactly: a pet's breed is in neither TSM's strings nor a battlepet link, so a pet key has no =.<breed>=; and TSM keeps only the bonus ids it considers relevant, so a TSM ledger row can name fewer bonuses than the Blizzard key for the same auction. Game currencies are instruments =currency:<id>= of kind =other=.

An instrument line carries =name=, =kind: item=, =category= (the item class), =parent= for a variant, and attrs =item_id=, =vendor_sell= (copper), =quality= (Blizzard's type string, =EPIC=), =item_level=, =pet_species_id=, =tsm_levels= and =tsm_modifiers=.

** Accounts

| Account          | Key                          | kind        | From                                                           |
|------------------+------------------------------+-------------+----------------------------------------------------------------|
| a character      | =<Name>-<Realm>=             | =character= | every source; =login= its folder; attrs class, level, race, faction, guild, played_seconds, login_account, zone, and per profession =profession:<Name>= (skill), =profession_max:<Name>= and =profession_secondary:<Name>= (true for Cooking, Fishing...) |
| a warband bank   | =warbank:<folder>=, or =warbank:<group>= when shared | =shared= | TSM's warband money and items, DataStore, Syndicator; =login= its folder, none when shared |
| a guild bank     | =guild:<Guild>-<Realm>=      | =guild=     | TSM's guild vaults, DataStore, Syndicator; the realm is the guild's home realm when Syndicator knows it (a guild on connected realms is seen from each), else the realm the winning copy was read on |

=last_seen= is a character's latest login or logout time from any source. =balance= lines carry a character's gold (the reconciled copy), the warband bank's gold and a guild's gold from TSM's guild gold log, each dated by its source when it has a date.

** Logins in the export

A =login= line describes one account folder; accounts name it in =login=. It is an additive change to protocol 1, but not one an older VENTURE can ignore: protocol 1 refuses an unknown message type and an unknown member of =account=, and either fails the whole push. Against a VENTURE that predates logins, set ~venture_logins: false~ (or pass ~--no-logins~ to ~export~ / ~venture push~): the stream is then what it was before, and =attrs.login_account=, sent either way on characters and per-account warbands, still says which folder an account came from.

#+begin_src json
{"type":"login","key":"ZAKMANN","name":"Main","kind":"game_account","group":"bnet-main","attrs":{"region":"us"}}
#+end_src

| Member  | Value                                                                      |
|---------+----------------------------------------------------------------------------|
| =key=   | the folder name (with a =hosts:= prefix); stable, what =account.login= names |
| =name=  | the =account_labels= label, else =WoW<n>= for a =<number>#<n>= folder, else the folder name |
| =kind=  | =game_account= (the contract's set: =game_account=, =platform_account=, =other=) |
| =group= | the =battlenet_groups= entry, when the folder is in one                    |
| =attrs= | =region=                                                                   |

- Characters carry =login=: the folder whose data they came from.
- Per-account warbands carry =login= and =attrs.login_account=; a shared warband carries neither, but =attrs.login_group= and =attrs.login_accounts= (the folders whose copies were compared).
- Guild banks carry no =login=: a guild bank is reached from any login with a character in the guild.
- A shared warband is sent only when every folder of its group was read. With one of them filtered out (~--login~) or on a machine that could not be read, the copies at hand may not include the freshest, and its snapshot would restate the bank from an older view; it is left out whole and the reason is in ~export --check~'s "Left out" table.
- ~export --check~ validates login lines (key, kind from the closed set, flat attrs within the account caps, one line per key) and =account.login=.

** What a snapshot covers

An =account_snapshot= tells VENTURE "these kinds of this account, as of =at=, are all of them"; rows of a covered kind that the stream does not restate are deleted. So a kind is covered only when some source actually read it for that account, even when it is empty:

| Kind        | Covered when                                                                                                  |
|-------------+---------------------------------------------------------------------------------------------------------------|
| =holdings=  | TSM has a quantity table for the owner, or DataStore/Syndicator has any container set or currency list for it (an empty warband TSM or Syndicator read is covered; see [[*Warband banks: per account or shared][Warband banks]]) |
| =positions= | DataStore scanned the character's auctions, or Syndicator has its auction list (TSM keeps no auction ids)      |
| =inbound=   | DataStore or Syndicator has the character's mailbox (an empty mailbox that was read is covered, and empties it in VENTURE) |
| =balances=  | the account's gold is known                                                                                   |

A TSM-only character is therefore restated for holdings and balances only, and VENTURE keeps whatever positions and mail an earlier, richer export sent. =at= is when WoW last wrote the files the account came from (their newest mtime; the remote mirror keeps the remote mtimes). An export of older files -- a stale mirror on another machine -- is older, and VENTURE skips it instead of rolling the account back. Push with the same ~--sources~ every time: switching DataStore off makes the next push restate holdings without the places only DataStore knew.

** Holdings, positions, inbound

- *Holdings* are the reconciled holdings (see [[*Reconciliation: which copy wins][Reconciliation]]), one line per account, place and instrument (two item strings naming one key are summed), plus currencies at place =currency=. Places are the contract's: =bag=, =bank=, =reagent_bank=, =void=, =mail=, =auction=, =warbank=, =guild=, =other=.
- *Positions* are posted auctions: =id= is the auction id, =venue= the realm slug, =price= the per-unit buyout, =bid= the per-unit bid when there is one, =expires_at= the expiry. VENTURE requires a buyout and an expiry, so an auction with no known buyout (Syndicator-only, typically one that has already expired and is in the mail) or no expiry is left out and counted, never sent with an invented price; it is still a holding at place =auction=. Expired auctions still listed are sent: they are what "collect" means.
- *Inbound* is one line per mail entry with money, an item or cash on delivery (DataStore already keeps one entry per attachment); bare letters are left out. The id hashes the character, sender, subject, the time the mailbox was read, the expiry, the item, its count and the money, plus an occurrence number for identical entries. It is stable until the mailbox is read again, when the snapshot restates the mailbox under new ids.

** The ledger

Each TSM ledger row is a =txn=: =sale=, =buy=, =income=, =expense=, =expired= or =cancelled=. Sales are after the AH cut, as TSM stores them; =amount= is unit price times quantity for sales and buys, the amount for income and expense, and absent for expired and cancelled rows. =counterparty= is TSM's other party, =source= its source (Auction, Vendor, Trade, COD) or money type (Postage, Repair Bill).

The id is =tsm-= and the first 32 hex digits of SHA-256 over realm, kind, TSM's own time, player, other party, item, stack size, price, source and an occurrence number (rows of one CSV identical apart from the quantity, counted in file order). Never the quantity: TSM merges a later identical sale into an existing row by growing its quantity, and VENTURE updates the row with the same id. The same row in two accounts' files (TSM account sync) is one row, with the larger quantity. A row TSM dated in the future (mail expiry math) is dated at the file's save time, so its =at= moves when the file is saved again; its id does not.

Internal transfers (trades and mail between your own characters) are left out unless ~--include-internal~: protocol 1 has no member to mark them, they are not business income or expense, and a txn once stored is never removed. ~--since~/~--until~ narrow the ledger only; everything else is always complete.

** AuctionDB

One =snapshot= per venue, dated with the venue's AppData download time, then a =stat= per instrument:

| Venue                    | Figures                                                                                       |
|--------------------------+-----------------------------------------------------------------------------------------------|
| each realm               | =min= (min buyout), =market= (market value), =historical=, =listings= (auction count)          |
| =commodities-<region>=   | the same for the region-wide commodity market (shared by every realm since 9.2.7)            |
| =region-<region>=        | =market= (region market value), =historical= (region historical), =sale_avg=, =sale_rate= (0-1), =sold_per_day= |

~--market scope~ (the default) sends only items you hold, post, get by mail or ever traded, plus every item in a TSM group, and marks each snapshot =complete: false=: it is a sample, and a complete snapshot would mark everything it left out as sold out. ~--market all~ sends everything AppData has (tens of megabytes) with =complete: true=; ~--market none~ sends no market data. VENTURE ignores a snapshot it has already applied (same venue, same time), so a push between two TSM app downloads adds nothing to the history.

** Push

~tsmctl venture push~ takes a lock (=~/.cache/tsmctl/venture/push.lock=, so overlapping triggers run one after another), waits for the files to settle with ~--settle 20s~ (local installs only: WoW writes every addon's file one after another on logout), exports into a spooled buffer while checking every line against the contract (an export that breaks it is never sent), and POSTs it to =/api/v1/feeds/<source>/push= with =Content-Type: application/x-ndjson=. ~--wait~ adds =?wait=1=: VENTURE answers when the run is written (up to 120 s) and tsmctl prints the run -- status, rows written, refusals and its notes. ~--organization ID~ adds =organization_id=. ~--if-changed~ skips the request when the body is byte-for-byte what was last accepted for this server, source and organization (=~/.cache/tsmctl/venture/last-push-*.sha256=, written only after a push VENTURE took).

It works wherever tsmctl does: on mob-zach it reads the local install; elsewhere it reads the ssh mirror as every other command does.

| Exit | Meaning                                                                            |
|------+------------------------------------------------------------------------------------|
| 0    | pushed (queued, or with ~--wait~ a run that ended =ok=), or nothing changed            |
| 1    | a local error: settings, token, unreadable data, an export that breaks the contract  |
| 2    | a usage error                                                                      |
| 3    | the server could not be reached (connection, DNS, TLS)                             |
| 4    | VENTURE refused the push: an HTTP error (401, 403, 404, 409 not a push source or switched off, 413, 415) or a redirect |
| 5    | ~--wait~: the run failed (a line broke the protocol; nothing of it was stored)      |
| 6    | ~--wait~: the run was partial, or not finished within VENTURE's wait               |

~tsmctl venture status~ prints the settings (never the token, only where it came from), =GET /api/v1/health= (no credentials sent) and the source's newest runs from =GET /api/v1/feeds/<source>/runs= (~--runs N~). Exit 3 when the server cannot be reached.

** Recipes

VENTURE's Crafting page prices recipes from a =blizzard_auctions= data source's =import_recipes= action. Battle.net's profession tree would import every recipe of an expansion, known or not, and its recipe ids are not spell ids; TSM's crafts are exactly what your characters know, with everything a recipe needs. ~tsmctl venture recipes~ sends them as that action's =recipes= parameter:

#+begin_src json
{"recipes": [{"spell_id": 3755, "name": "Linen Bag", "profession": "Tailoring", "category": "Bags",
              "item": 4238, "quantity": 1, "reagents": [{"item": 2996, "quantity": 3}, {"item": 2321, "quantity": 3}],
              "known_by": ["Drheals-Thorium Brotherhood"]}],
 "create_products": true, "venture_id": 2}
#+end_src

to =POST /api/v1/data_source/<venture_recipe_source>/actions/import_recipes= (with =organization_id=), 250 recipes a request. =category= is DataStore's for the same spell id when a character's list has one; =known_by= holds the knowers' account keys (=<Name>-<Realm>=, as their =account= lines name them), so VENTURE can say who can craft what. A craft that makes something other than an item, or whose only reagents are optional, is left out and counted. With =venture_recipe_venture= set, VENTURE makes a product for an item that has none; without it such recipes are skipped and the answer says which.

With =venture_recipe_source= in the config, ~venture push~ sends them too, after a push VENTURE took, and only when they changed since the last set it accepted (=~/.cache/tsmctl/venture/last-recipes-*.sha256=): learning a recipe sends them again, a sale does not. ~--no-recipes~ skips them for one push. So the systemd units need nothing more. A refused set exits 4 and is sent again next time.

** The API token

- It is read from =$TSMCTL_VENTURE_TOKEN=, else from the token file (=venture_token_file=, default =~/.config/tsmctl/venture-token= when it exists), else from venturectl's =$VENTURE_TOKEN=. There is no command-line option for it: argv is readable by every user through =/proc=.
- The file must be a regular file owned by you with no group or other permission bits (~chmod 600~); anything looser is refused before anything is sent. Its first line is the token.
- Both variables are removed from tsmctl's environment once read, so the ssh child of a remote read never inherits them.
- It goes only in the =Authorization: Bearer= header. Plain =http://= is refused unless the server is this machine (=localhost=, =127.0.0.0/8=, =::1=) or ~--allow-http~ is given; TLS certificates are verified against the system store; redirects are refused rather than followed, because a redirect would carry the header to a host the response chose.

#+begin_src bash
install -m 600 /dev/null ~/.config/tsmctl/venture-token
$EDITOR ~/.config/tsmctl/venture-token   # paste the token
tsmctl venture status
#+end_src

** systemd user units

Three units push on logout, with a timer as a fallback:

| Unit                            | Where it comes from                                                                                       |
|---------------------------------+-----------------------------------------------------------------------------------------------------------|
| =tsmctl-venture-push.service=   | shipped in the dotfiles (=.config/systemd/user=, stowed into =~/.config/systemd/user=): a oneshot running ~tsmctl -q venture push --settle 20s --if-changed --wait~ |
| =tsmctl-venture-push.timer=     | shipped in the dotfiles: every 30 minutes (and 5 minutes after boot) for a missed event or a server that was down; ~--if-changed~ makes an idle run one export and no request |
| =tsmctl-venture-push.path=      | generated on mob-zach by ~tsmctl venture install-units~: =PathChanged== for every SavedVariables file tsmctl reads (TradeSkillMaster.lua, DataStore*.lua, Syndicator.lua) by absolute path, because path units do not expand globs |

~tsmctl venture install-units~ prints all three to stdout and the commands to run on stderr. ~--write~ writes them to =~/.config/systemd/user=: the =.path= unit is always refreshed (re-run it after adding a WoW account or an addon), a =.service= or =.timer= that already exists is kept, and a symlink (a stowed unit) is never written through. It never runs systemctl; enable them yourself:

#+begin_src bash
tsmctl venture install-units            # read what it would write
tsmctl venture install-units --write
systemctl --user daemon-reload
systemctl --user enable --now tsmctl-venture-push.path tsmctl-venture-push.timer
systemctl --user start tsmctl-venture-push.service   # one push now
journalctl --user -u tsmctl-venture-push.service -n 50
#+end_src

The service reads =venture_url=, =venture_source= and the token file from the config, so nothing secret is in a unit file.

* Remote mirroring

1. One ssh call lists, under =WTF/Account/*/SavedVariables/=, exactly these names with =find -type f \( -name ... \) -printf '%T@ %s %p'=: =TradeSkillMaster.lua=, =DataStore.lua=, =DataStore_Characters.lua=, =DataStore_Auctions.lua=, =DataStore_Mails.lua=, =DataStore_Containers.lua=, =DataStore_Currencies.lua=, =DataStore_Crafts.lua= and =Syndicator.lua=, plus =AppData.lua=. Any other name in the reply is ignored. Every source is mirrored whatever ~--sources~ says, so switching sources never needs a re-copy.
2. Files whose mtime or size differ from =~/.cache/tsmctl/hosts/<host>/manifest_retail_.json= (or are missing) are streamed with one =tar cf -= call and unpacked with Python's =tarfile=. Only regular files with exactly the requested names are accepted; anything else in the stream (another name, a symlink, a directory) is skipped, and a requested file that does not arrive as a regular file fails the sync. Each file is written to a =.part= file and renamed, and keeps the remote mtime.
3. Files that vanished remotely are removed from the cache.

A first sync is about 18 MB (DataStore adds a few hundred KB and Syndicator about 1 MB); later runs only copy what changed (usually AppData every hour and SavedVariables after a logout).

* Limitations

- SavedVariables only change on logout or ~/reload~; the AH ledger and holdings trail a live session.
- =auctionQuantity= is what was posted at the last logout, not what is posted now. DataStore's auction list is as of the last AH visit; an auction whose expiry has passed has either sold or come back by mail, and nothing on disk says which until the mailbox is opened.
- Neither DataStore nor Syndicator records cash-on-delivery amounts, so the =cod= field of mail is 0 unless known.
- DataStore keeps no timestamp for the warband bank and Syndicator keeps none at all, so they only win where no dated source has the data.
- A shared warband's freshest copy is judged by timestamps that are not exactly "when the bank was last seen": TSM dates its copy by the last change of the warband's gold, the others by when WoW wrote the folder's file, which a login that never opened the bank also updates.
- Whether the warband is per WoW account or shared across a Battle.net account's licences is not in the files; =warband:= says it.
- TSM's =expiringAuction= is each character's first expiry as TSM last saw it and can be stale; it is used only for characters without DataStore or Syndicator auction data.
- TSM does not record AH deposits, so expiries cost more than the ledger shows.
- Crafting costs are not modelled: crafted items sold have no cost basis. Converting one item into another (opening Card of Omens, for example) shows as a buy of one item and sales of others; use ~pnl --item A --item B~ to see such a venture as one P&L.
- Gold history resolution is 1,000g on retail.
- Market data is the TSM app's last download (realm scans hourly, region stats daily).
- VENTURE export: pet keys have no breed and TSM ledger rows can carry fewer bonus ids than Blizzard's key (see [[*Instrument keys][Instrument keys]]); auctions without a known buyout are not sent as positions; internal transfers need ~--include-internal~ and cannot be taken back once pushed; inbound ids change when a mailbox is read again.

* Tests

=tests/scripts/test_tsmctl.py= (stdlib ~unittest~) builds a synthetic two-account install with an AppData file and checks the Lua parser, item-cache decoding, base-32 and x1000 scaling, price expressions, dedupe of synced rows, future-date clamping, internal-transfer exclusion, flips/sell-through math, valuation, deals, every command in every output format, clean errors, roam-node saving with stable IDs and index linking, and that the WoW files are byte-for-byte unchanged afterwards.

A second synthetic install has TSM, DataStore and Syndicator for one account, written the way the client writes them (CRLF, positional nils, sparse arrays with explicit index keys, packed values, a legacy 10-bit slot, a battle pet). It checks the decoders (item links, slots, currency naming), the reconciliation rule and each place it applies (gold, bags, bank, warbank, a guild on two connected realms, auctions, mail, currencies), the auction join on the auction id, ~--sources~ through the option and =TSMCTL_SOURCES=, ~attention~'s order and thresholds, every new command in all six output formats, and that missing or corrupt optional files only warn. A third install has DataStore only, with corrupt files. The ssh mirror is tested with a fake ssh: it must list every source's file names and refuse anything else in the listing or the tar stream, including a symlink under a requested name.

The VENTURE tests check every exported line against an independent reading of the contract written in the test (required members per kind, unknown members absent on the account kinds, decimal strings with at most four places, zoned times, integer counts, flat attrs, txn rules per kind, one snapshot per account ahead of its rows, unique ids), the Blizzard key mapping (plain, unsorted and repeated bonuses, modifiers and TSM's level-only form dropped, pets), that coverage is never claimed without detail data (a TSM-only character, ~--sources tsm~), that the same files give the same bytes, that txn ids survive a TSM merge that grows a quantity (and a merge only one account's copy saw), the market scope, ~--check~ and the 0600 ~--file~. ~venture push~ is tested against a stdlib =http.server= stand-in: the Authorization header and content type, the token never in any process's command line nor printed, ~--wait~, ~--if-changed~, every exit code, a refused redirect, plain http refused, the token file's permission check and source order, and the lock; ~venture status~ sends no credentials to the health check; TSM's crafts are loaded and merged across realms, named onto ~get recipes~, sent as profession attrs on accounts, and ~venture recipes~ / ~venture push~ send them in the documented shape only when they changed (and again after a refusal); ~install-units~ lists every SavedVariables file, prints exactly the units shipped in the dotfiles and never writes through a stowed symlink.

The login tests build a third synthetic install with two folders (=MAIN= and =ALT#1=), each with its own characters, ledger, TSM first-expiry times and warband copy, in two variants: ALT's copy fresher and full, and ALT's copy older and empty. They check the nested config syntax and its refusals (a folder in two groups, an empty group, an unknown warband mode or =hosts= key, a bad prefix), that the sample config's examples parse, ~--login~ by label and by group, login lines in the export against the contract (key, label as name, group, ordering before the accounts) and ~export --check~ counting them, the checker's own refusals for login lines, an empty warband exported as covered with a zero balance and no rows, a shared warband taking the freshest copy's gold and items in both directions and never their sum while the commands count it once, a shared warband left out when a sharing login is filtered out, a group named like a folder refused, grouping by login in ~get chars~, ~attention~ (text and ~--by login~) and ~pnl~, and =hosts:= (two installs merged, a folder name on both refused without a prefix, a machine that cannot be read skipped, ~--wow-dir~ reading one).
